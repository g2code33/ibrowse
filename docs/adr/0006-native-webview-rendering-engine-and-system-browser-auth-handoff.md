# ADR 0006: Native WebContentsView Rendering Engine and System-Browser Sign-In Handoff

## Status
Accepted

## Context
`BrowserShell.js` (the shared floating-browser UI used by every platform target) rendered every visited website inside a plain HTML `<iframe>`. This works for sites that allow being embedded, but a large share of real-world sites - Google, GitHub, Facebook, Microsoft, Amazon, and others - send `X-Frame-Options` / CSP `frame-ancestors` response headers that **forbid any iframe from embedding them at all**. That restriction is enforced by the target site and by the browser engine itself; no amount of configuration on Yayra's own Content-Security-Policy can override a restriction the remote site enforces against being framed. Users navigating to these sites saw either a blank frame or the browser's own inline "refused to connect" error rendered inside the tab.

A second, related but distinct problem: Google (and Apple, Microsoft) actively detect and refuse to complete OAuth/sign-in flows inside *any* embedded browser surface - including a legitimate native webview, not just an `<iframe>` - as an anti-phishing measure ([Google's documented policy](https://developers.google.com/identity/protocols/oauth2/policies#embedded-webviews)). This cannot be bypassed or spoofed; Google's own guidance for native/desktop/mobile apps is to open sign-in in the user's actual system browser.

This repository already has an ADR (0001) describing a long-term target architecture of fully native, per-platform browser engines (`browser-android` via `android.webkit.WebView`, `browser-windows` via WebView2, `browser-linux` via WebKitGTK). Those packages (`packages/browser-windows/src/WindowsWebView2Engine.js`, `packages/browser-linux/src/LinuxWebKitEngine.js`, plus native `.c`/`.cpp` companions) exist today purely as **contract-level simulations exercised by their own unit tests** - they are never imported by `electron/main.cjs`, `electron/preload.cjs`, or `BrowserShell.js`, and therefore have no bearing on what the shipped desktop app actually renders. The desktop app that is actually built and distributed runs on **Electron** (`electron/main.cjs`), hosting `BrowserShell.js` inside Electron's own Chromium renderer. Any real fix had to target that actual, shipping code path rather than the aspirational native-engine packages.

## Decision
**Electron desktop (Windows, Linux):** Real website content is now rendered through Electron's `WebContentsView` (the current, non-deprecated replacement for `BrowserView`; see `electron/webviewBridge.cjs`), attached as a sibling OS surface directly to the application window's `contentView`, positioned over an invisible HTML placeholder element tracked with a `ResizeObserver`. A `WebContentsView` is a first-class sibling surface, not a nested browsing context, so `X-Frame-Options` / `frame-ancestors` never apply to it. The renderer (`BrowserShell.js`) detects this capability via `window.yayra.webview` (exposed by `electron/preload.cjs`) and only falls back to the legacy `<iframe>` renderer when that bridge is absent.

**Identity-provider sign-in (all platforms):** Navigations to a static, auditable list of known sign-in hosts (`accounts.google.com`, `appleid.apple.com`, `login.live.com`, `login.microsoftonline.com`) are never embedded anywhere. On Electron they are hereby handed off via `shell.openExternal` from the main process (`electron/webviewBridge.cjs`). On Android/iOS (Capacitor) and plain web/PWA builds - which have no native webview bridge and still run `BrowserShell.js` inside one ordinary WebView/browser tab, subject to the exact same restrictions - the same hostname check (`BrowserShell.isSystemBrowserAuthHost`, kept in sync by hand with the Electron-side list) hands off via Capacitor's native in-app browser plugin (`@capacitor/browser`, Chrome Custom Tabs / SFSafariViewController) when running as a packaged native app, or a plain `window.open` new tab on the web/PWA build.

**Known frame-hostile sites (non-auth, e.g. general google.com/github.com browsing) on non-Electron platforms** continue to show an explicit in-app "this site can't be embedded" card with an open action, now routed through the same Capacitor-aware `openExternally()` helper instead of a raw `window.open` call, so the behavior is consistent and testable across platforms.

This is an incremental fix to the actually-shipping Electron/Capacitor/web code paths, not a rewrite of the ADR 0001 target architecture; it does not touch or depend on the `browser-windows`/`browser-linux` contract packages, which remain future-facing and unaffected.

## Consequences

### Positive
* Real-world sites that previously failed to load at all (Google, GitHub, etc.) now load correctly on Electron desktop, with no change to CSP relaxation that would weaken the app's own security posture.
* The floating browser's UI/UX (tab strip, resize/minimize/maximize/close, omnibox, history, bookmarks) is completely unchanged - only the content-rendering internals were touched.
* Sign-in handoff is implemented the way the identity providers themselves document as correct, rather than attempting to defeat anti-automation detection, on every platform that has this problem (desktop, mobile, and web).
* The fix and the sign-in-host list are unit-tested (`tests/electron-webview-bridge.test.mjs`, `tests/browser-shell-native-engine.test.mjs`, `tests/browser-shell-capacitor-handoff.test.mjs`) against mocked Electron/Capacitor APIs.

### Negative / Known limitations
* Electron itself cannot be launched inside this project's CI/dev sandbox, so `electron/webviewBridge.cjs` is verified only against a mocked `WebContentsView`/`ipcMain`/`shell` harness, never against a real Electron window. Manual verification on a real desktop build is still required before relying on this for a release.
* `goBack()` / `goForward()` on the native engine re-drive navigation by calling `ensure()` with the previously tracked URL rather than invoking Chromium's native `webContents.goBack()`/`goForward()` history traversal; this is functionally correct for URL display but does not share a single history-entry list with Electron's own back-forward cache. A future iteration could thread real back/forward state through if this proves insufficient.
* True per-tab native WebView replacement on Android/iOS (i.e., genuine OS-level sibling WebViews positioned under the floating tab strip, mirroring the Electron `WebContentsView` approach) is **not** implemented here. It would require a custom native Android (Kotlin) / iOS (Swift) Capacitor plugin, which cannot be built or tested in this environment (no Android SDK / Xcode toolchain available). Mobile still uses the existing single in-app WebView with the `<iframe>` fallback for embeddable sites, plus the new system-browser handoff for sign-in and frame-hostile hosts specifically.
* The sign-in host list is intentionally duplicated (once in `electron/webviewBridge.cjs` for the Electron main process, once in `BrowserShell.js` for the renderer/web/Capacitor bundle) because the two run in different module systems (CommonJS/Node vs. the browser ESM bundle) that cannot share an import without added build complexity; both copies carry a comment pointing at the other.
